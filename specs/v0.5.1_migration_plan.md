# v0.5.1 Migration Plan

Scope: production deployment hardening after the `v0.5.0` GEBCO_2026 data/API
upgrade. This plan intentionally separates "runtime/deployment migration" from
the already-completed "data source upgrade" so rollout and rollback stay simple.

## Goals

`v0.5.1` should deliver four things:

1. Move the production runtime from `Pipenv` to `uv` with a repo-local
   `./.venv`.
2. Replace `pygeos` usage in `src/polyhandler.py` with native Shapely 2 APIs.
3. Keep the existing production serving model:
   `pm2 -> gunicorn -> uvicorn worker -> FastAPI`.
4. Deploy safely to VM37 with a low-risk validation path and a clear rollback.

Non-goals:

* No GEBCO data re-conversion in `v0.5.1`.
* No NGINX reconfiguration unless deployment validation proves it necessary.
* No branch-flipping on a live working tree as the primary rollback mechanism.

## Safety Rules

These rules apply until an explicit cutover approval is given.

1. Do not interrupt the current production service on VM37.
2. Do not restart or reload the existing `pm2` app `gebco`.
3. Do not modify the live production bind on `127.0.0.1:8013`.
4. Do not change NGINX or public routing during preflight/staging.
5. All VM37 validation before cutover must run locally on a different port
   bound to loopback only, for example `127.0.0.1:18013`.
6. No cutover action is allowed until local VM37 smoke tests for point, line,
   and polygon mode pass on the non-production port.

## Key Decisions

### 1. Keep `gunicorn`

Do not simplify to raw `uvicorn` for this release.

Reasoning:

* the app is already in production
* `gunicorn + uvicorn worker` is a standard ASGI production setup
* graceful worker/process behavior is better defined than a single raw
  `uvicorn` process
* changing the process model at the same time as the package manager and
  geometry engine adds unnecessary risk

### 2. Use root `uv`, not `dev2026` as production

Do not reuse `dev2026/pyproject.toml` as the production env.

Reasoning:

* `dev2026/` is tooling-oriented and Python 3.13-specific
* production currently runs against a different dependency set and code path
* mixing offline conversion dependencies with production runtime makes upgrades
  harder to reason about

Instead:

* keep `dev2026/` as tooling
* add a separate root `pyproject.toml` for production
* build `/home/odbadmin/python/gebco/.venv` from that root definition

### 3. Keep Python 3.11 on production first

`v0.5.1` should migrate package management first, not Python version.

Reasoning:

* current production is already on Python 3.11
* Shapely 2 works on Python 3.11
* moving to `uv` does not require moving to Python 3.13
* avoiding a Python-version change keeps rollback simpler

This means:

* root `pyproject.toml` should target Python 3.11
* `dev2026/` can continue using 3.13 independently

### 4. Treat `pygeos -> shapely` as required before deploy

The shim in `dev2026/scripts/_pygeos_shim.py` proved the compatibility path, but
it should not become the production architecture.

`v0.5.1` should make `src/polyhandler.py` import and call Shapely 2 directly.

## Work Breakdown

### Phase A. Root runtime migration to `uv`

Deliverables:

* root `pyproject.toml`
* optional root `uv.lock`
* root `.venv` build instructions
* removal of production dependency on `Pipenv`

Tasks:

1. Create root `pyproject.toml` based on the current production dependency set.
2. Keep dependency versions conservative for the first pass:
   * start from current `Pipfile` / `requirements.txt`
   * only change what is required for the `pygeos -> shapely` migration
3. Generate `uv.lock`.
4. Verify local startup via:
   * `uv sync`
   * `uv run gunicorn gebco_app:app -k uvicorn.workers.UvicornWorker ...`
5. Update docs so production bootstrap no longer points at `pipenv`.

Files expected to change:

* `/Users/cywhale/proj/gebco/pyproject.toml` (new)
* `/Users/cywhale/proj/gebco/uv.lock` (new)
* possibly `requirements.txt`
* possibly `README.md`
* possibly `AGENTS.md`

### Phase B. `src/polyhandler.py` migration to Shapely 2

Deliverables:

* no `pygeos` import in production code
* equivalent polygon endpoint behavior
* updated tests / regression scripts

Tasks:

1. Replace `pygeos` imports and calls with native Shapely 2 APIs.
2. Keep the current response contract untouched:
   * same mode auto-detection from `jsonsrc`
   * same sampling behavior (`sample=5` default for polygon mode)
   * same supported GeoJSON shapes
3. Re-run:
   * `dev2026/scripts/verify_polygon_meridian.py`
   * `dev2026/scripts/verify_polyhandler_endpoint.py`
4. Add one minimal benchmark or timing note for polygon mode to confirm no
   obvious regression.

Files expected to change:

* `/Users/cywhale/proj/gebco/src/polyhandler.py`
* possibly `/Users/cywhale/proj/gebco/gebco_app.py`
* possibly `/Users/cywhale/proj/gebco/dev2026/README.md`
* possibly `/Users/cywhale/proj/gebco/dev2026/TESTING.md`
* possibly `/Users/cywhale/proj/gebco/AGENTS.md`

Files expected to become removable or less central:

* `/Users/cywhale/proj/gebco/dev2026/scripts/_pygeos_shim.py`

### Phase C. PM2 runtime switch

Deliverables:

* `pm2` app continues to be named `gebco`
* launch command uses root `.venv`
* no dependence on `pipenv run`

Tasks:

1. Update
   [conf/ecosystem.config.js](/Users/cywhale/proj/gebco/conf/ecosystem.config.js:1)
   to call root `.venv` binaries explicitly.
2. Remove `--reload` for production unless there is a hard operational need to
   keep it.
3. Keep bind target on `127.0.0.1:8013` so NGINX does not need to change.
4. Re-check whether `--keyfile` / `--certfile` are actually needed behind
   NGINX. If NGINX terminates TLS and proxies locally, these flags may be
   unnecessary and should be removed only after confirming current traffic flow.

Preferred launch style:

```bash
./.venv/bin/gunicorn gebco_app:app \
  -w 2 \
  -k uvicorn.workers.UvicornWorker \
  -b 127.0.0.1:8013
```

Keep worker count conservative unless VM37 sizing suggests otherwise.

### Phase D. VM37 deployment procedure

This should be done in two steps: staging on the live VM, then cutover.

#### D1. Preflight on VM37

Allowed scope:

* only `/home/odbadmin/python/gebco`
* only commands needed to update this deployment

Tasks:

1. Confirm `uv` availability on VM37.
2. Confirm which Python 3.11 interpreter `uv` will use.
3. Inspect current `pm2` process definition and logs.
4. Confirm whether `main` has local-only uncommitted changes on the VM.

#### D2. Safe code update

Preferred order:

1. Fetch remote.
2. Check out `gebco_2026_api` or a release tag derived from it once tags are in
   use.
3. Build root `.venv` via `uv sync`.
4. Verify the canonical Zarr path exists on VM37:
   * `data/GEBCO_2026_sub_ice_topo.zarr`
5. Run local smoke checks before touching `pm2`.

Smoke checks:

* import app module
* start app on a temporary local-only port such as `127.0.0.1:18013`
* `curl` point mode
* `curl` line mode
* `curl` polygon mode
* optional direct local benchmark

#### D3. Cutover

1. Update `conf/ecosystem.config.js` on the deployed branch.
2. `pm2 restart gebco` or `pm2 start ...` if the app definition changes.
3. Verify:
   * `pm2 status`
   * local curl against `127.0.0.1:8013`
   * public HTTPS endpoint once local checks pass

#### D4. Rollback

Rollback should not require reconstructing data files.

Preferred rollback levers:

1. revert to previous git commit/tag in the same repo
2. restore previous `conf/ecosystem.config.js`
3. restart `pm2`

Avoid rollback by ad hoc manual edits where possible.

## Recommended Execution Order

1. Write and land root production `pyproject.toml`.
2. Build local root `.venv` and prove local startup under `uv`.
3. Migrate `src/polyhandler.py` to Shapely 2.
4. Re-run the polygon/meridian regression scripts.
5. Update `conf/ecosystem.config.js`.
6. Commit as `v0.5.1` work on `gebco_2026_api`.
7. Preflight VM37.
8. Deploy to VM37 with local-only smoke tests first.
9. Cut over `pm2`.
10. Verify public endpoint.

## Risks To Watch

* root production dependency drift when converting from `Pipfile` to
  `pyproject.toml`
* subtle polygon behavior changes during the Shapely 2 rewrite
* VM37 having local state that does not match GitHub
* `pm2` command differences if the current deployment relies on shell-specific
  behavior
* `gunicorn` TLS flags being redundant or interacting oddly with NGINX

## Open Questions Before Implementation

1. Should root `requirements.txt` remain maintained alongside `pyproject.toml`,
   or become generated/secondary?
2. Is `--reload` currently relied upon operationally on VM37, or is it just a
   leftover development convenience?
3. Are `--keyfile` / `--certfile` actually needed in the local gunicorn bind
   path behind NGINX?
4. Does VM37 already have a Python 3.11 runtime visible to `uv`, or will
   `uv python install 3.11` be needed?

## Definition Of Done

`v0.5.1` is complete when all of the following are true:

* production runtime no longer depends on `Pipenv`
* production uses repo-local `./.venv`
* `src/polyhandler.py` no longer depends on `pygeos`
* `pm2` starts the app successfully via `uv`-managed environment
* point, line, and polygon smoke tests pass on VM37
* rollback steps are documented and tested at least once locally/in staging
