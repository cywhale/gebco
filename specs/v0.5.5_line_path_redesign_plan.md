# v0.5.5 Line / MultiLine Performance Redesign Plan

## Background

`v0.5.3` and `v0.5.4` hardened and accelerated the API, but they did
not finish the non-polygon path:

- `v0.5.3` added backend guards so obviously dangerous requests return
  `413` instead of risking worker OOM
- `v0.5.4` fixed the Python hot loops in `zprofile.py` /
  `xmeridian.py`, and redesigned polygon mode around batching +
  `contains_xy`

Those changes were correct, but they left one unresolved question:

> For large line / multi-line transects, are we guarding the *real*
> memory bottleneck, or only a rough bbox proxy?

Live usage and the public A/B checks showed this question matters in
practice. A transect like:

```text
lon=-155,-143,-131,-118,-105,-92
lat=-30,-18,-6,6,18,28
mode=zonly
sample=3
```

is scientifically reasonable for basin-scale route planning or profile
inspection. The legacy endpoint (`ecodata.odb.ntu.edu.tw`, `v0.5.2`)
serves it successfully, and the user reports it is still acceptable even
with front-end rendering included. The current `v0.5.4` line guard would
reject it because its enclosing bbox is slightly above the present
`2e8` threshold.

Important historical detail:

- the public `sample` query parameter is intentionally **polygon-only**
- line / point / `MultiLineString` requests still run through
  `zprofile(..., sample=1)` regardless of the caller's `sample=N`
  request

So when this plan talks about large line transects, it is always talking
about the real `sample=1` cost path. This work does **not** assume that
line-path sampling already exists.

So `v0.5.5` is not about loosening guards blindly. It is about moving
the guard closer to the **actual materialization cost**, so large but
reasonable transects can pass when their true touched-cell workload is
safe.

## Goal

Redesign the non-polygon GEBCO read path so large line and
`MultiLineString` requests are bounded by the **cells actually touched by
the transect**, not by eager materialization of the entire enclosing
bbox.

This is a follow-up to:

- `v0.5.3`: backend bbox guards (`GEBCO_MAX_BBOX_CELLS_LINE`)
- `v0.5.4`: line hot-loop (`np.append -> list`) and polygon batching

The evidence gathered after `v0.5.4` shows the remaining bottleneck is
not the Python loop anymore; it is the data access pattern in
`src/zprofile.py`.

## Improvement target

The target is not simply "make the cap bigger".

The target is:

1. make the line / `MultiLineString` pipeline load data in a way that is
   proportional to the **real cells or chunks touched**
2. reduce wasted materialization so that most scientifically reasonable
   requests fall naturally below the final guard
3. only then re-evaluate the cap, using measured materialized workload
   rather than bbox area alone

In other words, the desired end-state is:

- most legitimate requests do **not** need special-case cap exceptions
- the pipeline itself becomes more efficient and memory-rational
- the remaining cap is a real safety guard, not a stand-in for an
  inefficient read strategy

## Current diagnosis

## Observed behaviour

From `dev2026/scripts/investigate_line_path_caps.py`:

- diagonal under-cap line (`bbox ≈ 1.87e8`) returns only `~14k` rows but
  still uses `~0.86 GB` RSS in direct-path measurement
- another diagonal just under cap (`bbox ≈ 1.94e8`) behaves similarly
- `MultiLineString` can stay under the per-part cap yet aggregate to
  `>1 GB` RSS because each segment is processed independently
- wide horizontal / vertical lines with **more output rows** can be
  cheaper than the diagonal cases because their bbox is much smaller

This proves:

1. output row count is **not** the dominant cost driver
2. the current cap is a rough bbox proxy, not a direct measure of memory
3. `MultiLineString` has an aggregate blind spot

## Evidence collected so far

### W1 direct-path evidence

Current code path on the local 2026 Zarr:

| case | bbox / subset cells | output rows | touched cells | touched chunks | direct wall | RSS delta |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| `q5_diag_under_cap` | `1.867e8 / 1.867e8` | `14,406` | `14,401` | `25` | `~269 ms` | `~864 MB` |
| `q8_diag_over_cap` | `2.106e8 / 2.106e8` | `15,126` | `15,121` | `26` | `~182 ms` | `~951 MB` |
| `multiline_aggregate_heavy` | `part_sum 3.788e8` | `33,368` | `33,362` | `48` (union) | `~469 ms` | `~1.26 GB` |

This is the key mismatch:

- current subset materialization is on the order of **hundreds of
  millions of cells**
- actual touched cells are only **tens of thousands**

### W1 stage breakdown

For `q5_diag_under_cap`, current direct-path timing is approximately:

- planner / line walk: `~32 ms`
- `ds.sel(...)`: `~2 ms`
- `.values` materialization: `~142 ms`
- final gather from materialized subset: `~0.3 ms`

This shows the true hot spot is `.values`, not bbox math, not
`crossBoundary`, and not the final point selection.

### W2 prototype evidence

The first sparse-read prototype (`dev2026/scripts/prototype_sparse_line_read.py`)
already demonstrates the intended direction without touching production
code:

| case | current subset MB | sparse chunk MB | current `.values` | sparse prototype | byte-equal |
| --- | ---: | ---: | ---: | ---: | --- |
| `q5_diag_under_cap` | `356.2 MB` | `86.9 MB` | `146.4 ms` | `21.8 ms` | yes |
| `q8_diag_over_cap` | `401.7 MB` | `90.4 MB` | `104.9 ms` | `23.3 ms` | yes |
| `multiline_aggregate_heavy` | `722.6 MB` | `166.9 MB` | `139.3 ms` | `45.8 ms` | yes |

This is not yet production integration, but it is already strong
evidence that the present bottleneck is architectural, not fundamental.

## What this plan is *not* trying to do

This plan is not trying to:

- make line requests arbitrarily large
- remove backend guards
- optimize around front-end rendering limits
- redesign polygon mode again

The purpose is narrower:

- stop wasting memory and decompression work on the full bbox when only
  a sparse transect is needed
- let the final guard operate on a more faithful cost model

## Root cause in code

Current line path in `src/zprofile.py` does this:

1. compute the exact line-walk cell indices into `idx1_buf`
2. compute a large bbox around the whole line
3. slice the Zarr-backed dataset:

```python
ds_s1 = ds.sel(lon=slice(mlon0x, mlon1, sample), lat=slice(mlat0x, mlat1, sample))
```

4. then materialize the entire bbox subset:

```python
xt1 = ds_s1["elevation"].values[tuple(idx1.T)]
```

The expensive step is `.values`, not `ds.sel(...)` itself.

The current pipeline therefore already knows the exact target cells, but
still decompresses the entire bbox before selecting them.

## Design principle for v0.5.5

Rejecting on bbox alone is too early.

The guard should move closer to the **actual materialization step**:

- estimate or count the chunks / cells that will truly be loaded
- prefer a sparse or chunk-grouped read path
- only reject when the projected materialized workload itself exceeds a
  safe threshold

Put differently:

- bbox is a cheap heuristic
- chunk-touch set or actual selected-cell set is the real cost model

## Current status of the plan

At the time of this document revision:

- `W1` is effectively complete as an evidence-gathering phase
- `W2` has both a working prototype and a first-pass production
  integration for `mode=zonly` line / `MultiLineString` requests
- `W3` and `W4` are still design / integration work

So the next implementation step is **not** to revisit the cap first. It
is to decide how the sparse prototype should be folded into the real
`zprofile()` path.

Current first-pass limitation:

- sparse chunk-aware reads are only enabled for `mode=zonly`
  line / `MultiLineString` requests
- distance-producing line requests still use the legacy bbox path in
  this phase to keep the rollout scoped

## Proposed implementation order

## W1. Instrument the current line path more precisely

Before algorithm changes, add one more level of breakdown around the
materialization step:

- bbox shape in cells
- line output rows
- unique target cell count
- estimated chunk-touch count
- actual `.values` wall time
- RSS delta

Deliverables:

- extend `dev2026/scripts/investigate_line_path_caps.py`
- add a smaller direct profiler focused on `zprofile()` read stages

Acceptance:

- for each near-cap case we can state whether cost is better explained by
  bbox cells, unique target cells, or chunk touches

## W2. Prototype chunk-aware sparse read

Minimal viable redesign:

1. keep the existing line-walk that produces `idx1_buf`
2. convert `idx1_buf` into unique `(lat_idx, lon_idx)` cells
3. group those cells by chunk
4. read only the touched chunks
5. harvest the required cells from those chunk-local arrays

Important:

- do not require one remote/Zarr access per cell
- the unit of work should be chunk, not individual point
- maintain byte-equal output ordering with current API

Candidate strategies:

### Strategy A. Chunk-grouped direct array access

- inspect Zarr chunk shape for `elevation`
- map each requested `(lat_idx, lon_idx)` to a chunk key
- read each touched chunk once
- gather values from in-chunk offsets

This is the most direct way to align load with actual touched cells.

### Strategy B. Row-band grouping

If chunk-level access through xarray is awkward, a transitional approach
is:

- group requested cells into narrow row bands
- materialize only those row bands, not the full bbox
- gather target cells from each band

This is less ideal than chunk-aware reads, but still much closer to the
real touched cells than the current full-bbox materialization.

## Planned production code changes

The current expectation is that the real implementation will center on
`src/zprofile.py`.

Most likely code changes:

1. split current line path into two explicit phases:
   - **planner**: build ordered target-cell path and deduplicated cell
     set
   - **reader**: fetch only the touched storage units and reconstruct the
     ordered `z` values
2. add a sparse reader helper, likely private to `zprofile.py` at first
3. preserve current output ordering and response semantics exactly
4. extend `MultiLineString` handling so aggregate touched workload is
   visible before the whole request is executed

Candidate internal helpers:

- `_plan_line_cells(...)`
- `_read_sparse_chunks(...)`
- `_estimate_materialized_bytes(...)`
- `_check_multiline_budget(...)`

Exact helper names are not fixed, but the architectural split is.

### Single source of truth requirement

The planner logic must not live in two diverging copies.

Right now `dev2026/scripts/investigate_line_path_caps.py` contains a
measurement-only fork of the line walk. That is acceptable for W1, but
the production implementation should extract the planner into a shared
module, for example:

- `src/line_planner.py`

Then:

- `src/zprofile.py` imports and uses it
- `dev2026/scripts/investigate_line_path_caps.py` imports and uses it
- `dev2026/scripts/prototype_sparse_line_read.py` imports and uses it

This avoids drift when future cross-meridian or planner fixes happen.

## W3. MultiLineString aggregate accounting

Current behaviour treats each part independently for the cap.

Need to distinguish three different concerns:

1. **per-part worst case**
   - any individual part may still be too expensive on its own
2. **request-level planned work**
   - a `MultiLineString` with many individually-safe parts can still be
     expensive overall
3. **process RSS high-water**
   - Python / allocator / worker heap may keep RSS elevated even when
     parts are processed sequentially

The plan must not over-design this prematurely. The first production
goal is:

- expose enough planning metadata to tell which of the three concerns is
  actually binding in real runs
- guarantee that `MultiLineString` does not bypass safety simply because
  each part is individually under the old raw-bbox cap

So W3 should begin with:

- a per-part planner pass over all parts
- request-level summary metrics:
  - per-part max touched chunks / bytes
  - request-level sum / union touched chunks
  - projected materialized bytes if processed sequentially

Only after those measurements should we decide whether the production
guard is:

- strictly per-part
- request-level total
- or a mixed rule

Until aggregate measurements say otherwise, the first production pass
should ship with:

- a per-part chunk / materialized-byte budget
- plus a request-level summary log line containing:
  - `touched_chunks_sum`
  - `touched_chunks_union`
  - `projected_bytes_sum`
  - `projected_bytes_union`

This makes the "observe first" policy concrete, instead of leaving it as
an open-ended TODO.

## W4. Re-specify the line guard

Only after W2 / W3 measurements:

- replace or supplement `GEBCO_MAX_BBOX_CELLS_LINE`
- preferred basis:
  - touched chunk count
  - projected materialized cells
  - projected materialized bytes

Possible result:

- keep bbox as a cheap pre-check with a very high ceiling
- add the real guard at the sparse-read planning stage

The important policy point is:

- `v0.5.5` should not remove safety
- it should move safety to the layer that better matches actual memory
  use

That means the final cap may become:

- a touched-chunk ceiling
- a projected materialized-byte ceiling
- or a two-stage rule: loose bbox sanity check + strict sparse-read
  budget

### Short-line fallback

The sparse reader should not be forced onto every tiny request.

For short or compact line requests, the current bbox path may still be
cheaper than chunk-grouped sparse reads because:

- sparse planning has its own overhead
- chunk reads still decompress whole chunks

So the production implementation should include a fallback rule, for
example:

- if `bbox_subset_cells` is below a small threshold, keep the current
  direct bbox materialization path
- or if projected sparse chunk bytes are not meaningfully better than
  bbox materialization bytes, keep the current path

The exact threshold should be an env-controlled knob and measured, not
hard-coded by guesswork.

Suggested starting rule:

- if `bbox_subset_cells < 1_000_000`, keep the current direct bbox path
- env knob: `GEBCO_LINE_SPARSE_MIN_CELLS=1000000`

This is only a first-pass value and should be re-tuned after the first
implementation benchmark round.

If new env knobs are introduced during implementation, prefer the
following naming direction:

- `GEBCO_MAX_LINE_BBOX_CELLS` as the clearer long-term name
  - keep `GEBCO_MAX_BBOX_CELLS_LINE` as a backwards-compatible alias
- `GEBCO_MAX_LINE_CHUNKS` for a chunk-count guard
- `GEBCO_LINE_SPARSE_MIN_CELLS` for short-line fallback
- keep polygon knob names unchanged unless there is a separate reason to
  rename them

## Cases to keep

Reuse the near-cap cases already introduced in
`dev2026/scripts/investigate_line_path_caps.py`:

- `q5_diag_under_cap`
- `q8_diag_over_cap`
- `diag_under_close_cap`
- `horiz_wide_lowbbox`
- `vert_wide_lowbbox`

These are useful because they separate:

- large bbox / modest output
- modest bbox / large output
- single line vs multiline aggregate work

## Correctness gates

The redesign must preserve output values and order.

Required:

1. existing test suite still passes
2. existing cross-0 / cross-180 verification still passes
3. new large-line regression cases compare old vs new code path bytewise
   on:
   - row count
   - lon / lat arrays
   - z array
4. `MultiLineString` output remains byte-equal
5. add planner contract unit tests, e.g. `tests/test_line_planner.py`,
   covering:
   - one-point input
   - ordinary 2-point line
   - diagonal line
   - cross-meridian line
   - inverse map / dedupe reconstruction
   - degenerate tiny segments

### Cross-meridian planner contract

The planner must preserve the semantics introduced by
`xmeridian.crossBoundary`:

- inserted boundary-adjacent breakpoints remain explicit
- the planner output must contain enough segmentation metadata to avoid
  accidental cross-segment assumptions downstream
- sparse reconstruction must preserve output ordering across segment
  boundaries exactly

## Performance gates

The following are the intended directional outcomes.

These are intentionally phrased as goals first; final numbers should be
locked after the prototype shows what is feasible.

### Expected improvements

1. diagonal near-cap line:
   - substantial RSS reduction from `~0.8 GB`
   - wall time should no longer be dominated by full-bbox materialization
2. `MultiLineString` aggregate-heavy case:
   - significantly lower aggregate RSS than current `~1.1 GB`
   - better scaling under `c2/c4`
3. over-cap-like transects:
   - if sparse touched-cell workload is reasonable, they should become
     admissible instead of being rejected solely by bbox

### Final acceptance to define after W2 prototype

Once chunk-aware or row-band sparse reads are implemented, define:

- new wall/RSS targets for `q5`, `diag_under_close_cap`, and
  `multiline_aggregate_heavy`
- revised cap basis and default

The current prototype evidence suggests the final acceptance should be
framed around:

- byte-equal correctness
- large reduction in materialized bytes
- large reduction in `.values` / read-stage wall time
- improved aggregate `MultiLineString` behaviour

not merely around total request wall time in isolation.

### Concrete implementation-ready acceptance draft

Based on the current prototype, the implementation phase should target:

1. `q5_diag_under_cap`
   - read-stage wall (`.values` replacement) at least `3×` lower than the
     current path
   - projected materialized bytes at least `3×` lower than the current
     bbox subset
2. `q8_diag_over_cap`
   - same `≥3×` read-stage and materialized-byte reduction
   - correctness byte-equal to the current no-cap reference path
3. `multiline_aggregate_heavy`
   - read-stage wall at least `3×` lower than the current path
   - projected materialized bytes at least `3×` lower than the current
     sequential bbox materialization sum
4. short-line / compact-line cases
   - no material regression versus `v0.5.4`
5. all accepted 200-cases
   - byte-equal `longitude`, `latitude`, `z`
   - if distance mode is involved in follow-up tests, `distance` must
     remain byte-equal too

These thresholds can be tightened later, but they are concrete enough to
review an implementation PR against.

## Known risk

The main risk is over-correcting toward per-cell access, which could
increase overhead if implemented naively.

The redesign must remain chunk-aware; otherwise it may trade one kind of
slowness for another.

Another implementation detail to preserve:

- production should not keep opening duplicate dataset handles just to
  discover chunk shape or access the Zarr array
- the final implementation should derive what it needs from the existing
  app/runtime dataset handle where possible

The current prototype is allowed to open both xarray and raw zarr as an
experiment; production integration should avoid redundant openings.

## Decision trigger for cap retuning

Do **not** retune `GEBCO_MAX_BBOX_CELLS_LINE` first.

Retune only after:

1. sparse-read prototype exists
2. near-cap cases are re-measured
3. aggregate `MultiLineString` behaviour is understood
4. the production integration path is profiled under loopback /
   concurrency as well as direct path

At that point we can set a cap that reflects **actual materialized
work**, not merely bbox area.
