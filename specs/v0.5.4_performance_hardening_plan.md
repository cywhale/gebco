# v0.5.4 Performance Hardening Plan

## 1. Purpose

v0.5.3 proved that the remaining risk is not mainly "missing guards".
The deeper issue is that some hot paths still do too much work per
request:

* long polylines spend unnecessary time in repeated `np.append(...)`
  reallocations,
* polygon mode expands the full bbox into dense arrays before masking,
  so backend cost is often dominated by bbox size and geometry
  complexity, not by returned row count.

Therefore v0.5.4 should focus on **algorithmic and data-flow
improvements**, not on tightening `MAX_POLYGON_CELLS` alone.


## 2. High-Level Goals

1. Reduce line/polyline hot-path complexity from repeated dynamic NumPy
   reallocations to amortized linear accumulation.
2. Reduce polygon-mode CPU and RSS by avoiding the current
   `meshgrid -> shapely.points -> contains(all points)` full-bbox pattern
   wherever possible.
3. Preserve the current API contract:
   * same query params
   * same response schema
   * same polygon sampling semantics (`sample=5` default on polygon mode)
   * same cross-0 / cross-180 correctness
4. Rebuild the validation suite so correctness and performance are both
   first-class acceptance gates.

## 4. Problem Breakdown

### P1. Long polyline path is still O(n²)

Current issue:

* `src/zprofile.py` and `src/xmeridian.py` repeatedly do
  `np.append(arr, x, axis=None)` and similar patterns.
* Every append reallocates and copies.
* Long input lines therefore scale poorly.

Impact:

* mostly line / polyline mode
* also affects cross-meridian preprocessing

### P2. Polygon path materializes full bbox working sets

Current issue:

`src/polyhandler.py` currently does roughly:

1. subset whole bbox
2. `meshgrid(lon, lat)`
3. build one point geometry per cell
4. run `contains()` across every point
5. mask elevation

This means:

* CPU cost scales with **all bbox cells**
* memory cost scales with **all bbox cells**
* final returned rows are often a poor predictor of backend cost

This was demonstrated by Phase D2:

* thin ribbon polygon: bad at ~`1.05e6` raw bbox cells with only
  ~`2k` estimated output rows
* cross-180 thin polygon: ~`112 s / 8.3 GB RSS` while estimated rows were
  only ~`132k`


## 5. Proposed Workstreams

## W1. H9 refactor — list accumulation for line/polyline hot paths

### Goal

Replace repeated `np.append(...)` with Python-list accumulation followed
by one `np.asarray(...)` per final structure.

### Files

* `src/zprofile.py`
* `src/xmeridian.py`
* `gebco_app.py` (minor H13 follow-up)

### Design

Replace patterns like:

```python
idx1 = np.append(idx1, [[...]], axis=0)
loc1 = np.append(loc1, [[...]], axis=0)
dis1 = np.append(dis1, value, axis=None)
```

with:

```python
idx_buf.append((..., ...))
loc_buf.append((..., ...))
dis_buf.append(value)
```

then once near return:

```python
idx1 = np.asarray(idx_buf, dtype=np.int16)
loc1 = np.asarray(loc_buf, dtype=float)
dis1 = np.asarray(dis_buf, dtype=float)
```

Also land the minor v0.5.3 H13 cleanup here:

* split `_zprofile_df` / `_response_from_df`
* let request logging read row counts directly
* remove the current JSON round-trip row counting in `gebco_app.py`

### Expected payoff

* 3×–10× speedup on long polyline path
* no material change on single-point path
* no schema / value change

### Risk

* off-by-one differences in distance accumulation
* breakpoints around 0° / 180° must remain byte-equal


## W2. Polygon algorithm redesign — avoid full dense point construction

### Goal

Lower polygon-mode CPU and RSS by reducing per-cell geometry creation
and avoiding unnecessary full-bbox expansion.

### Design principles

1. Do not start by constructing one Shapely point per cell unless there
   is no cheaper filter left.
2. Prefer row/block-wise filtering before point-in-polygon.
3. Treat cross-180 polygons as a first-class path, not just a side case.

### Minimal viable v0.5.4 scope

v0.5.4 should ship **W2-B only** as the required redesign.

#### W2-B. Row-wise or chunk-wise mask generation

Instead of one giant `meshgrid`, process the bbox in smaller units:

* row batches, or
* fixed-size tiles

This bounds peak RSS.

Minimal pseudo-code:

```python
BATCH = 5000  # tune empirically
for row_start in range(0, len(lats), BATCH):
    chunk_lats = lats[row_start:row_start + BATCH]
    chunk_lon_mesh, chunk_lat_mesh = np.meshgrid(lons, chunk_lats)
    pts = shapely.points(chunk_lon_mesh.ravel(), chunk_lat_mesh.ravel())
    mask = shapely.contains(poly, pts).reshape(chunk_lon_mesh.shape)
    chunk_elev = sub["elevation"].values[row_start:row_start + BATCH][mask]
    # accumulate lon/lat/z into output buffers, flush chunk temporaries
```

This is deliberately narrow:

* it should cut peak RSS from "whole bbox" to roughly `BATCH × n_lons`,
* it preserves the existing exact geometry semantics,
* it avoids turning v0.5.4 into a full scanline-geometry rewrite.

#### W2-A. Cheap bounding-strip prefilter (follow-up, not required for v0.5.4)

Potential future step:

* compute polygon intersections with horizontal strips/lines,
* derive candidate longitude intervals,
* only materialize candidate columns inside those intervals.

This is promising, but it is a separate algorithmic step and should not
block the row-batch MVP.

#### W2-C. Optional exact point-in-polygon only after coarse candidate selection (follow-up)

After row/interval filtering, if exact geometry membership is still
needed, run `contains()` only on a much smaller candidate set.

### Pre-work profiling requirement

Before touching `polyhandler.py`, run one `cProfile` pass on the
Phase D2 `cross180_thin` archetype and record the hottest frames in
`TESTING.md` Phase G preamble. The point is to confirm whether the
current 112 s bottleneck is dominated by:

* `shapely.points(...)`,
* `shapely.contains(...)`,
* `meshgrid`,
* or DataFrame/materialization overhead.

The row-batch redesign is still the planned MVP, but the profile result
must be captured first so later reviewers can see whether W2-B is
expected to improve mainly RSS, or both RSS and wall time.

### Explicit non-goal

Do not try to optimize by changing user-visible sampling rules.
`sample=5` behavior remains contractually the same.

  redesign as a later task

## 8. New Performance Verification

### P-Bench-1. Long polyline benchmark

Purpose:

* validate H9 gain

Method:

* sparse style — 2-vertex polyline spanning ~20° (asymptotic regime)
* dense style — n input vertices over small span (segment-level only)
* compare before/after on direct `zprofile()` path
* additionally run `dev2026/scripts/profile_sparse_polyline.py` for
  per-stage wall decomposition (crossBoundary / ds.sel / .values /
  inner_walk / buffers→asarray)

Acceptance:

* **sparse-style median: ≥ 3× speedup on total wall**
* decomposition profile on the final branch should show the remaining
  wall is mostly Zarr/xarray rather than H9's inner loop
* no regression on single-point latency
* no regression on dense-style (modest improvement only, allowed)
Final Mac result on canonical 2026 Zarr (recorded in `TESTING.md`
Phase F): sparse `206.26 ms → 22.94 ms` (`8.99×`), dense
`237.44 ms → 15.71 ms` (`15.11×`). The stage-level decomposition
still matters because after H9 lands the remaining wall is mostly
`values_materialise`, but that is now an explanation of the residual
cost rather than a reason to relax the total-wall target.

### P-Bench-2. Polygon sparse-shape benchmark

Purpose:

* validate `polyhandler` redesign

Method:

Use 3 archetypes:

* thin ribbon
* coastal jagged
* cross-180 thin

For each record:

* wall time
* RSS delta
* row count

Acceptance:

* correctness unchanged
* thin ribbon wall time ≤ `0.5 s` at the D2 knee-size probe
  (`~1.05e6` raw bbox cells)
* coastal wall time ≤ `1.5 s` at the current D2 baseline shape
* cross-180 thin wall time ≤ `30 s` and RSS delta ≤ `2000 MB` at the
  D2 probe size (`~4.65e7` raw bbox cells)

These are intentionally concrete so PR2 review cannot hide behind
"material improvement" phrasing.

### P-Bench-3. Existing 1M-row polygon parity benchmark

Reuse the VM37/production-style benchmark already in `TESTING.md`.

Acceptance:

* no regression versus current `main`

## 12. Acceptance Criteria

v0.5.4 is done only if all are true:

1. `uv run --group dev pytest tests/` passes.
2. `verify_polygon_meridian.py` passes unchanged, plus new `T7`.
3. `verify_polyhandler_endpoint.py` passes unchanged.
4. `verify_api_vs_netcdf.py` still passes.
5. Long polyline benchmark meets P-Bench-1 acceptance:
   sparse-style total wall ≥ 3× faster than v0.5.3 baseline, with the
   decomposition profile showing that the remaining wall is mostly
   Zarr/xarray rather than H9's inner loop.
6. Polygon sparse-shape benchmark meets the concrete targets above:
   * thin ribbon ≤ `0.5 s` at the D2 knee-size probe,
   * coastal ≤ `1.5 s` at its D2 baseline shape,
   * cross-180 thin ≤ `30 s` and ≤ `2000 MB` RSS at the D2 probe size.
7. No regression in the existing large polygon parity benchmark.
8. `TESTING.md` records before/after numbers, not just intentions.


## 13. Recommendation

Do not spend more v0.5.3 effort trying to mathematically perfect
`MAX_POLYGON_CELLS`.

The best next investment is:

1. land H9,
2. redesign polygon internals with the row-batch MVP,
3. then re-measure,
4. only then revisit polygon cap policy.

That sequence attacks the actual bottleneck instead of overfitting the
guard around an inefficient implementation.
